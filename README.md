# 风声再临 · 线上版（核心战斗模块 + 数据配置工具）

技术栈：**React 18 + Vite + TypeScript**，无 Canvas、无游戏引擎。
美术暂用「颜色 + 文字」表达（红 / 蓝 / 黑情报、九种功能牌），先把规则跑通。

---

## 一、快速开始

```bash
npm install

npm run dev        # 只起前端 → http://localhost:5173
npm run server     # 只起联机服务端 → ws://localhost:8787
npm run dev:all    # 前端 + 服务端一起起（开发）

npm run serve      # 生产：构建 + 单端口对外服务 → http://localhost:8787
```

生产环境只开**一个端口**：`npm run serve` 把 `dist/` 和 WebSocket 一起挂在 8787 上。
客户端在生产环境走同源（`location.host`），所以不用写任何反向代理配置就能直接玩。
想挂到 80/443 也可以，把整个站点反代到 8787（WebSocket 记得透传 `Upgrade` / `Connection` 头）：

```nginx
location / {
  proxy_pass http://127.0.0.1:8787;
  proxy_http_version 1.1;
  proxy_set_header Upgrade $http_upgrade;
  proxy_set_header Connection "upgrade";
  proxy_set_header Host $host;
}
```

探活与指标：`GET /healthz`（极轻，给进程守护用）、`GET /stats`（连接数 / 房间数 / 限流次数 / 内存）。

**让同一个 wifi 下的朋友进来**：服务端监听所有网卡，启动时会直接打印可用地址：

```
[AbS] 已启动：http://localhost:8787 （静态资源与 WebSocket 同端口）
[AbS] 局域网：http://192.168.1.23:8787  ← 同一个 wifi 下的朋友用这个
```

把那行地址（不是 `localhost`）发给他们就行。客户端在生产环境用 `location.host` 连 WebSocket，
所以换 IP 访问时连接地址会自己跟着变，不需要改任何配置。
跨网络（不在同一个 wifi）需要自己做端口映射或反代到公网，服务端不内置这一层。

**放到公网（Render 免费层）**：仓库根目录已经带了 `render.yaml`，
在 Render 控制台 New → Blueprint → 选这个仓库 → Apply，不用手填任何命令：

| 配置 | 值 |
|---|---|
| Build | `npm ci --include=dev && npm run build` |
| Start | `npm start` |
| 健康检查 | `/healthz` |
| 环境变量 | `ABS_DATA_DIR=off`（临时文件系统上写快照没有意义） |

免费层的限制要先知道：0.1 CPU / 512MB、**15 分钟没有入站流量（含 WebSocket 消息）就休眠**、
唤醒约 1 分钟、随时可能被重启。一局游戏里 WebSocket 一直在收发，不会中途睡；
只有「开局前第一下」需要唤醒 —— **自己先打开一次把实例叫醒，再把链接发给朋友**。

> ⚠️ 两个和部署绑死的前提，改动时别踩：
> 1. `tsx` 和 `ws` **必须留在 `dependencies`**（不是 devDependencies）——
>    `npm start` 用 tsx 跑服务端、服务端 `import 'ws'`，而云平台默认 `npm ci --omit=dev`，
>    放进 dev 就会 `Cannot find package` 起不来。
> 2. `buildCommand` 要带 `--include=dev`：`vite` / `typescript` 在 devDependencies 里，
>    平台若预设 `NODE_ENV=production`，`npm ci` 会跳过它们，构建就找不到 vite。
>
> 若 `AbS` 不是仓库根目录（比如你建了个大仓库把它放进去），Apply 时把 Blueprint 路径填成 `AbS/render.yaml`。

前端有三种本地玩法（不需要服务端）：

| 模式 | 说明 |
|---|---|
| 单人 + AI 陪练 | 你坐 1 号位，其余由 AI 填充。用来熟悉规则、验证数值 |
| 单机热座 | 同一台设备轮流操作，视角自动切到当前行动者 |
| 上帝视角 | 所有身份与手牌公开，用来看流程、抓 bug |

联机玩法在「联机对局」页签：

1. 进大厅看**公开房间列表**，或者自己**建一个**（房间号留空会自动分配，4 位、去掉了 0/O/1/I 这些容易念错的字符）
2. 把房间号发给朋友，他们按号进来；房主选总人数，空位自动补 AI
3. 对局中每个操作点有 **30 秒倒计时**，超时或掉线自动交给 AI 托管，本人点「我回来了」立刻收回
4. 刷新页面 / 断网恢复会**自动回到原座位**（座位保留 5 分钟），不用重新进房
5. 房间页可以「复制邀请链接」（`?room=XXXX`），点开链接的人会自动带入房间号
6. 已经开局的房间也能进，但只能**观战**：看得到公开信息，看不到任何人的手牌和身份
7. 上一局打完、还没开下一局时，房间会显示「可加入下一局」—— 迟到的人这时能直接进来打，
   不用等大家回大厅重建（他会**顶掉一个机器人**，不会把对局人数撑大），
   而且**落后一轮** —— 你看到的是上一轮结束时的局面，当前轮里发生的事一概看不到。
   不延迟的话观众能实时报点，等于开图
8. 建房时可以设密码（大厅里只显示一个「密码」标记，不显示密码本身）。私密房的观战同样要密码
9. 打完一局**不用回大厅**：结算页点「再来一局」是给自己投一票，**全员准备好自动开下一局**，
   座位、昵称、密码都保留。有人先走了也不影响剩下的人开（走掉的座位会被摘掉，不会变成 AI 空位）

`ui-online` 用假 WebSocket 而不是真服务端，是因为它要验的是**客户端状态机**：
断线多久、重连退避几次、重连时到底发的是 `resume` 还是 `join`。
真服务端会把这些混在一起还带网络抖动；假 socket 能精确控制每一帧。

`npm run shots` 是**给人看的**，不是断言：DOM 测试能证明「元素存在」，
但证明不了「CSS 写歪了」「字被挤成两行」「横幅盖住了牌」。
它会用系统 Chrome 真开两个页面打一局，把每一步截图存到 `shots/`。
`scripts/shots-autopilot.ts` 单独验证托管条与断线重连（需要服务端用短超时启动，
否则要干等 30 秒）；`scripts/shots-spectate.ts` 验证观战视角与邀请链接；
`scripts/shots-latejoin.ts` 验证「朋友打完了才来」这条路径。

当前规模：引擎冒烟 10 局 · 单项规则 38 项 · 本地对局交互 16 项 · 联机界面 114 项 · 联机链路 97 项。

## 四、引擎设计（三条硬规则）

**1. 引擎不知道 React 存在。**
`applyCommand(state, pack, cmd)` 是唯一入口，所有合法性校验都在这里。UI 不做任何规则判断，
只负责把玩家意图翻译成 `Command`。所以同一份规则可以同时跑在浏览器、Node 服务端和测试脚本里。

**2. 状态是纯数据。**
`GameState` 可 JSON 序列化 / `structuredClone`。重连、复盘、AI 推演、快照比对都靠这一点。

**3. `pending` 由状态推导，不手工维护。**
`refreshPending(state, pack)` 从 `phase` / `flow` / `window` 反推出「现在该谁做什么」。
手写 `pending` 迟早会和真实状态漂移 —— 这是回合制引擎最常见的 bug 源。

### 回合流程

```
出牌阶段(action) → 情报阶段(intel) → 情报传递 → 弃牌阶段(discard) → 下一位
```

情报传递有四个响应点：

1. **传出**：选牌 + 选方式（密电朝下 / 文本朝上 / 直达指定）
2. **逐人经过**：每经过一个人，其他人可以【截获】
3. **到达接收者**：接收者可以【破译】看牌、或用【退回】弹回，或收下 / 拒收
4. **拒收则继续传**：密电 / 文本继续向下传，最后传回出牌者（不得拒收）；直达被拒则回到出牌者面前

功能牌打出后先进**响应窗口**，其他人可以用【识破】抵销；无人识破才真正生效。窗口支持嵌套。

## 五、规则实现范围（v1）

**已实现**

- 87 张基础牌：情报 45 + 功能 42，颜色分布 红 32 / 蓝 32 / 黑 23
- 九种功能牌全部可用：锁定、调虎离山、退回、截获、破译、识破、烧毁、真伪莫辨、试探
- 8 个示例角色，技能**真的生效**（见下表），不是占位文本
- 开局 **3 选 1 选角**：每人 3 个候选，已被别人选走的不会再出现
- **机密任务**：结构化数据（5 种类型），引擎实时判定，特工达成即单独获胜
- 3 / 4 / 5 / 6 / 7 人局，身份按 `gameConfig.json` 分配
- 胜负判定：任意一人集齐 3 张同色 → 该阵营胜；特工集齐 6 张真情报 → 特工胜
- 死亡判定：面前 3 张黑色情报出局；胜利优先于死亡结算
- 状态裁剪：朝下的密电内容在接收成功之前，任何客户端都拿不到牌面

| 情报贩子 | 【脱手】每局一次：收到黑色情报时自动弃置 | 面前情报总数达到 6 张 |
| 译码专家 | 【从容】手牌上限 +2 | 面前至少 3 张蓝色情报 |
| 播音员 | 【广播】传出的情报一律以「文本」方式传递 | 面前 4 张情报且没有黑色 |
| 硬骨头 | 【硬扛】每收到 1 张黑色情报，抽 1 张 | 除你之外有 3 人出局 |
| 哨兵 | 【反制】传出的情报被【截获】时，抽 1 张 | 存活到第 6 轮开始 |

> 机密任务是**结构化数据**（`holdColor` / `collectTotal` / `noBlackWith` / `othersDead` / `surviveRounds`），
> 文案由 `describeTask()` 从数据生成，配置工具里改的是字段而不是文本 —— 不会出现「文案说 3 张、判定看 4 张」。

新增技能的做法：在 `src/core/skills.ts` 的 `SKILLS` 里加一个钩子，再在 `characters.json` 里把 `skillId` 指过去。
**不用改引擎。**

## 六、数据与配置工具

四个数据文件在 `src/data/defaults/`，全部走 zod 校验：

- `cards.json` — 卡牌（id / 名称 / 颜色 / 传递方式 / 功能 / 效果文本）
- `characters.json` — 角色（id / 名称 / 是否隐藏 / 难度 / skillId / 技能文本 / 机密任务）
- `identities.json` — 三个阵营的名称与胜利条件文案
- `gameConfig.json` — 手牌上限、起始手牌、每回合抽牌、胜利所需情报数、死亡黑牌数、各人数身份配比

**改数据有两条路：**

1. **可视化编辑器**（推荐）—— 前端顶部「数据配置」页签。增删改卡牌 / 角色 / 身份 / 规则参数，
   实时校验并高亮错误，导出 JSON 覆盖 `defaults/` 下同名文件即可生效。
2. **直接改 JSON + 跑校验** —— `npm run validate`，适合进 CI 或批量改。

改完一定要跑一次 `npm run test`：数据合法 ≠ 规则跑得通（比如把胜利所需情报改成 10，
引擎不会报错，但一局会打不完）。

## 七、联机：房间 / 重连 / 超时托管 / 观战

### 反作弊

- 服务端 `server/index.ts` 是**权威端**：所有指令在服务端校验后结算，客户端只提交意图。
- 每次状态变化都按**每个玩家各自的视角**裁剪后再推（`redactState`），不是「推全量让前端自己藏」。
- 服务端持有 `playerId`（会话）与 `gamePlayerId`（引擎内 p0/p1…）两套 id，校验一律用后者。

**三种视角必须分清**（`src/core/redact.ts`）：

| viewerId | 看到什么 | 用在哪 |
|---|---|---|
| 某个玩家 id | 自己的手牌 + 公开信息 | 玩家 |
| `PUBLIC_VIEW` 常量 | 谁的手牌都看不到，身份也不公开 | **观战** |
| `null` | 全公开 | 本地热座 / 上帝视角 / 复盘，**服务端永不下发** |

观战**不能**复用 `null`：那是「全公开」，观众拿到它等于人手一个作弊器。
实现上 `PUBLIC_VIEW` 是一个绝不可能是玩家 id 的哨兵字符串，`players.find(p => p.id === viewerId)`
找不到人，于是 isSelf 全 false、hand 全 null、身份只在出局/结算后公开 —— 正好是旁观者该看到的。

**顺带修掉一个真漏洞**：开局日志原来写的是「对局开始（种子 XXXX，N 人局）」。
日志是广播文本，每个玩家和观众都能看到，而「种子 + 引擎」等于「牌堆顺序」——
拿着它就能算出朝下的牌是什么。现在日志只写人数，种子留在 `state.seed` 里，
由 `redactState` 控制只对上帝视角 / 结算后放行。

### 房间

| 行为 | 规则 |
|---|---|
| 建房 | 房间号可自填或自动分配（4 位，字母表去掉了 `0/O/1/I`） |
| 大厅 | 只列 `isPublic` 的房间，按创建时间倒序，最多 30 个 |
| 大厅的人数 | 同时报 `players`（占着座位的真人）和 `online`（真的连着的人）。**一个人都不在线的房间挂「无人在线」标记且不能点加入** —— 掉线有 5 分钟保座宽限期，这期间只报 `players` 的话，大厅会显示「2 / 7 人」而实际一个人都没有 |
| 加入 | 未开局、**或上一局已结束**，且未满 7 人才能进。对局进行中一律拒绝 |
| 密码 | 可选。**只标「有锁」，不告诉任何人密码是什么**；加入和观战都要过这一关 |
| 房主 | 建房者；房主掉线时自动转移给「还在线的下一位」，全掉光则置空 |
| 换座位 | 未开局或上一局已结束时可以换。**房主能换任意两个，其他人只能换自己和一个别人** |
| 下一局人数 | 房主能调机器人数量（结算阶段生效，真人座位不动） |
| 回收 | 15 秒一次巡检：未开局的掉线座位过 5 分钟移除；全房间没有活人则删房 |

**密码为什么不做成「大厅里看不见」**：藏起来的话，朋友连「我要进哪个房」都不知道。
所以房间照常列出来，只在房主名字后面挂一个「密码」标记；点「加入」时不发请求，
而是把房间号填好、把光标送到密码框 —— 发一个注定被拒的请求，用户还得自己猜为什么没反应。

密码明文存内存（不落盘、进程重启即丢），但**永远不下发**：`RoomSummary` 里只有
`hasPassword: boolean`，没有 `password` 字段。这一点有测试盯着（断言大厅列表的 JSON 里
不含密码串）。

### 重连：用 token，不用昵称

昵称会重名、会改，token 不会。服务端给每个座位发一个 `resumeToken`，客户端存
`localStorage['abs:seat:<房间号>']`。刷新页面 / 断网恢复时自动带 token 回原座，
**拿回的是同一个 `gamePlayerId`**（所以手牌、身份、面前的情报都还是你的）。

重连细节：

- 客户端断线后按 **400ms → 800 → 1.6s → … 封顶 5s** 退避重连，最多 8 次
- 心跳 **5 秒一次 ping，15 秒没 pong 判死**。这两个数字是和服务端 30 秒托管对齐的：
  客户端必须在「被判超时」之前发现自己掉线，否则玩家会先被 AI 接管，然后才看到「正在重连」
- **判死后不等 `onclose`**。拔网线 / 飞行模式 / 进隧道时，浏览器不会立刻触发 `close` ——
  它会一直等着连接恢复，可能几分钟都不回调。只靠事件的话界面会「看着像卡住」，
  所以心跳判死自己把状态推进到「重连中」（`downRef` 是 onclose 与心跳的同一个出口）
- 同一个 token 被新连接使用时，旧连接会被顶掉（防止刷新后两个标签页抢同一个座位）
- 回座失败（房间没了 / 座位过期）不会无限重试，直接回大厅并清掉本地凭证

### 主动离开 ≠ 掉线

这两个状态必须分开，否则两边的承诺会互相打架：

| | 服务端怎么处理 | 为什么 |
|---|---|---|
| 直接断开（关标签页 / 拔网线 / 刷新） | 座位保留 **5 分钟**，`connected=false`，对局中立刻交给 AI | 可能是 wifi 抖了一下，踢掉代价远大于留个空位 |
| 点「离开」/「退出观战」 | 先发 `{ t: 'leave' }`：不在对局中 → **座位立刻摘掉**、座位号重排；对局中 → 座位不能删（引擎状态会错位），只打 `left` 标记并交给 AI，等这局结束、下次开局时再摘 | 这是明确的意图，座位不该继续占着 |

只有 socket 关闭的话，服务端**没有任何办法**区分这两者。所以客户端的离开按钮会先发
`leave` 再断开 —— 否则走掉的人会白占 5 分钟，下一次开局还凭空多出一个 AI 空位。

`left` 是持久标记（会写进快照）：对局中离开的人，本局继续由 AI 代打，
但「再来一局」时不会再被拉进来。

`left` 座位的**全部连带影响**（这几条都是踩过的坑，改动时别只改一半）：

| 位置 | 行为 |
|---|---|
| 大厅人数 / 可加入性 | 不算进 `players`，也不占加入名额（否则显示 4/7 而实际只有 3 人） |
| 准备进度条 | 两边都不算 —— 既不是「在线」，也不是「等着开局的玩家」 |
| 房主转移 | 房主离开后**立刻**转给还在线的下一位，**对局中也转**。不转的话 `hostId` 会一直指着一个走了的人，本局打完后剩下的人里谁都不是房主，「调整人数」直接被挡 |
| 下一局人数 | 不计入「至少 3 人」的机器人数下限，并在重建座位表时清出去 |
| 房间回收 | 不算「还有活人」：全员离开后房间**立刻回收**，不占 5 分钟宽限期（大厅上挂一个 0 人房间纯属添乱） |
| 凭 token 回来 | 回来即清 `left` 标记、立刻交还控制权 —— 否则人明明在线，下一局开局时却被当成「走了」摘掉座位 |

主动离开是明确的意图，所以**不享受** 5 分钟反悔窗口；真反悔了重新进房就行。

界面上这两件事也必须分开说：`left` 标记会随 `room` 消息下发，座位卡显示
**「已离开 + AI 代打」**（灰色、整卡去饱和），而不是「掉线」（红色）。
都标成「掉线」的话，其他人会一直等他重连，结算页还会以为他只是网络不好。

对局中有人离开还会往**对局日志**写一行「某某离开了对局，之后由 AI 代打」。
走日志而不是弹一个提示，是因为日志跟着快照持久化 ——
刷新、重连、服务端重启之后，后来的人仍然能知道这个座位为什么在被 AI 打。

对局界面里的座位卡也会标「已离开」（整卡降透明度）。只靠日志不够：
日志会滚走，座位卡是常驻的，而「这个人还会不会回来」是会改变决策的信息。

### 超时托管

每个操作点 **30 秒**倒计时，`deadlineAt` 由服务端下发（绝对时间戳），客户端只负责渲染递减。
**客户端数到 0 不会自己替玩家行动** —— 本地时钟会被改、会切后台、会有网络延迟，判定权只在服务端。

超时或掉线 → 该座位标记 `autopilot`，由 AI 接管这一步**和后续所有决策**，其余人不用等。
本人回来点「我回来了」（或直接发一条指令）立刻交还控制权。

### 观战

观众和座位是**两套独立的数据结构**：`Room.seats` 里只有玩家，观众放在 `Room.spectators`
（一个 `Set<WebSocket>`）。不混在一起的原因很实际 —— 一旦观众进了 `seats`，
人数上限、房主转移、AI 补位、托管判定全都要多写一遍 `if (isSpectator)`。

| 行为 | 规则 |
|---|---|
| 入口 | 大厅里已开局的房间显示「观战」；也可以输房间号点「以观战身份进入」 |
| 门槛 | 只能看**已开局**的房间（没开局没什么可看的，直接加入就行） |
| 权限 | 不占座位、没有 token、发指令会被拒（「观战者不能操作对局」） |
| 重连 | 断线后重放 `spectate`，**不写座位存档** —— 否则刷新会拿空 token 去 resume |
| 房间没了 | 房间被回收 / 服务端重启后房间不在 → 回大厅并提示原因。`role` 在点「观战」时是**乐观**设置的，被拒后必须清掉，否则会永远停在「正在进入观战…」（这个坑踩过两次，见下） |
| 人数 | 房内玩家和房间页都能看到「N 人观战」 |
| 延迟 | **落后 1 轮**（`ABS_SPECTATOR_DELAY_ROUNDS`）。观众看到的是上一轮结束时的局面 |
| 界面 | 没有手牌条、没有操作区，换成一块观战面板（阶段 + 在等谁 + 为什么看不到牌） |

观众看不到手牌之后，界面下半部分会空出一大块，看起来像加载失败 ——
所以专门做了 `SpectatorPanel` 占住那块空间，而不是复用操作区的「等待」态。

#### 为什么是「落后一轮」而不是「延迟 30 秒」

第一版做的是固定 30 秒，跑起来发现两头不讨好：

- **慢局里太保守** —— 观众盯着半分钟前的选角画面干等，而那半分钟里对局其实毫无进展；
- **快局里又不够** —— 30 秒够看好几手了，报点照样有用。

按回合的语义是明确的：**当前这一轮里发生的任何事，观众都看不到**。它和回合制的节奏天然对齐，
也不需要拍脑袋定一个秒数。

代价是「一轮之内画面是静止的」。这不是 bug —— 观众看的就是上一轮结束时的牌桌。
所以状态栏写「慢 1 轮」、观战面板写「你看到的是第 N 轮结束时的局面，落后 1 轮」，
并且把面板上的时态改成「当时：出牌阶段 / 当时轮到 X」。
**用「正在」「等待」这种现在时是不行的** —— 观众会以为对局卡住了。

#### 手机上观众看得到什么（360×640 实测）

面板在竖屏上位于 4 张座位卡下面（`top 727`，折叠线 540），要滚到底才看得到 ——
所以**时态和阶段不能只写在面板里**，得挪到首屏就能看见的状态条上：

| 位置 | 观众版 | 为什么 |
|---|---|---|
| 状态条第 1 颗 | 「**当时** 第 N 轮」 | `view.round` 是旧画面的轮次，不写「当时」就是把旧局面说成现在。观众没有操作区，也没法靠「我能不能出牌」反推时态 |
| 状态条第 3 颗 | 阶段（「正在选角」「出牌阶段」…） | 玩家的阶段靠操作区按钮文案体现（「结束出牌」/「收下」），观众什么都没有 |
| 状态条 | **不写「等待：X」** | 观众不在等待任何东西；谁在动，座位卡的 `acting` 高亮已经说了 |
| 房间条 | **不写房间号、不写延迟** | 观众的房间里没有他的座位，房间号对他最没用；延迟对不能操作的人也没意义 |
| 机密任务条 | **不渲染** | 观众没有身份（`viewerId` 是 `PUBLIC_VIEW` 哨兵），目标条无处可挂 |

房间条那两颗不是「顺手删的」：实测 360 宽下「房间号 + 观战中 + 延迟 + 退出观战」
四颗一共要 384px，而可用宽度只有 324px，**必然折行**。更麻烦的是折不折取决于
「延迟」这颗**晚到**的 pill —— 首帧没有它时是 1 行（33px），1 秒后它到了就变 2 行（61px），
整块内容往下跳 28px。删掉这两颗之后稳定 1 行、还剩 77px 余量，
`npm run check:spectator` 会在「房主那边延迟已经测出来」之后再量，专门盯这一条。

横屏（`orientation: landscape and max-height: 520px`）是另一套：面板脱离文档流钉在右栏
（`position: fixed; top: 52px; right: 0; width: 320px`），否则右栏空着 320px、
面板却被挤到 `y=666`（屏高才 390）。这时状态条和面板会同时出现在屏幕上，
面板里的「当时：正在选角」和状态条的「正在选角」看起来重复 ——
**这是有意的**：竖屏上面板一滚就离开了状态条，它必须自己把话说全。

#### 实现

不是「先收着、过一轮再显示」——那要求客户端配合，改个 DevTools 就绕过了。
延迟发生在**服务端**：每次状态变化往 `room.specBuffer` 里塞一份「公开视角」快照
（带 `seq` 和 `round`），推送时取「最新一帧 `round <= 当前轮 - 1`」。

四个容易做错的地方：

1. **没有观众时也要存快照。** 否则观众「退出再进来」直接拿到当前状态，延迟等于不存在 ——
   这是个很好用的作弊手法。
2. **新观众进来时不能发 `room.state`**，要走和 flush 同一个 `specTarget()`。发当前状态等于绕过延迟。
3. **第 1 轮没有「上一轮」**，退到缓冲里最早的一帧（开局局面）——
   观众看到的是发牌完成的牌桌，而不是空白。
4. **帧标识用自增 `seq`，不能用时间戳。** 一次指令里可能同步推好几个状态，
   `Date.now()` 会撞在同一毫秒上，去重就会误判成「这帧已经发过了」，观众直接卡住。

另外两条特殊处理：对局结束时**立刻放行最后一帧**（让观众再等一轮才知道谁赢了，
除了折磨人没有任何意义）；给观众的 `deadlineAt` 一律传 `null` —— 那是过去某一刻的截止时间，
画出来只会是个 0 秒倒计时。

实测截图：玩家在**第 2 轮**、观众停在**第 1 轮**，面板写明「你看到的是第 1 轮结束时的局面」。
服务端测试里还有一条更硬的断言：连续采样 2.5 秒，玩家轮次减观众轮次**始终 >= 1**。

### 换座位与下一局人数

**换座位不是外观功能。** 这个游戏的**座位顺序 = 行动顺序 = 情报传递方向**，
所以红方的人想坐在盟友旁边（情报往下一家传时不经过敌人），蓝方同理。
座位定了就改不了的话，想调整只能重建房间、全员重进。

| 项 | 规则 | 为什么 |
|---|---|---|
| 谁能换 | 房主：任意两个座位；其他人：自己 ↔ 别人 | 房主负责组织牌桌；其他人能自己挪，但不该替别人决定 |
| 什么时候能换 | 未开局，或上一局已结束 | 对局中换座等于偷换行动顺序，是作弊 |
| 怎么操作 | 点一个座位选中，再点另一个完成交换（再点自己取消） | 比拖拽简单，手机上也能用 |
| 座位号 | 交换后仍然连续 `0..n-1` | 引擎按下标取「下一位玩家」，有空洞会直接崩 |
| 下一局人数 | 房主调机器人数量，真人座位与顺序不变，机器人补在后面 | 真人不会因为调人数被挪位置 |

房间页在座位表下面有一句说明：「座位顺序 = 行动顺序 = 情报传递方向。想让谁挨着谁，在这里调。」
不写这句的话，玩家会以为这只是在「把头像摆好看」。

**开局前会提醒「有人掉线」**：掉线的人还占着座位（5 分钟保座宽限期），开局时**照样算进人数**、
由 AI 代打 —— 这是刻意的，刷新页面的人不该被踢出去。但房主看到的「当前 3 人」里可能有一个不在，
不说清楚他就会以为「3 个人打」，实际是 2 个人 + 1 个 AI。所以人数那一行旁边会多一句红字：
「1 人掉线：开局后由 AI 代打，他们回来点「我回来了」就能收回。」

**结算页的入口**：结算浮层上有「调整座位 / 人数」这个文字按钮，点了才进房间页
（房间页里有「返回结算」退回去）。**不做成「对局一结束自动跳回房间页」** ——
那会把正在看结算、正在复盘的人直接掀桌。想去调的人自己点。

下一局一开（`gameOver` 变 false），这个临时房间页会自动收回，免得新一局的结算
又把人送进房间页。

### 再来一局

结算页的按钮**不是房主一键重开，而是准备投票**。

朋友局打完一局会复盘、会打字，房主一点就把画面重置掉，比不让重开更难受。
所以每人自己点「再来一局」，全员准备好才真正开局：

| 行为 | 规则 |
|---|---|
| 准备 | 点一下 = 准备，再点一下 = 取消（同一个按钮，能反悔） |
| 开局条件 | **在线真人**全部准备好；机器人不投票 |
| 掉线的人 | 按「自动准备」处理 —— 否则一个走了的人能把整桌卡在结算页 |
| 全员离线 | **不开局**。否则会开出一局谁也没在看的游戏，还把房间状态推进掉 |
| 离开的人 | 开局前从座位表摘掉（座位号重新排连续）。他上一局结束后点了「返回大厅」，座位还在 5 分钟宽限期里挂着，留着只会让新一局凭空多一个 AI 代打的空位 |
| 中途退出 | 结算页另有「返回大厅」，随时能走 |

「准备 3 / 5」**分子分母都只数在线真人**：把掉线的算进分母，会出现「差一个却开不了」的
自相矛盾文案；而把掉线的算进**分子**更糟 —— 3 人局里 1 人掉线、1 人点了准备、1 人没点，
进度条会显示「2 / 2 已准备」但游戏根本不开始（`allReady` 是 false），
玩家会盯着一个「已满」的进度条干等。掉线人数单独放在 `ready.offline` 里，
界面用一句话说明「N 人掉线（自动算准备）」。
全员掉线时是 `0 / 0`，界面不能把它当成「满了」——服务端有兜底不会开局。

### 结算阶段允许新人加入

上一版有个明显缺口：一局打完后房间仍然是 `started`，想换个人进来打下一局却进不来 ——
只能全员回大厅重建房间。而「朋友晚到十分钟」是朋友局里最常见的场景之一。

判定条件不是 `started`，而是**「已开局 + 已分出胜负」**：

```ts
function isGameOver(room: Room): boolean {
  return Boolean(room.started && room.state?.winner);
}
```

| 行为 | 规则 |
|---|---|
| 大厅显示 | `上一局已结束 · 2 / 7 人 · 可加入下一局`，按钮是「加入下一局」+「观战」 |
| 加入门槛 | `started && !gameOver` 才拒绝。对局进行中仍然是硬拦截 |
| 座位 | **顶掉一个机器人**，而不是追加。房主开局选的是「3 人局」，多来一个朋友不该把对局悄悄变成 4 人 —— 补位用的机器人本来就是凑数的，真人到了就该让位；没有机器人可顶时才追加 |
| 准备 | 自动算准备。他已经用「加入」表达过想打了，再点一次「准备」是多余操作 |
| 状态 | **不推上一局的状态**。他此时 `gamePlayerId` 是 null，`sendStateTo` 有守卫直接跳过 —— 否则他拿到的是一个「谁的手牌都看得见」的视角 |
| 界面 | 房间页显示「上一局已结束 · 等下一局」+ 准备进度，没有「开始对局」（房主不能一键绕过别人已经点过的准备） |

这个状态没法用消息流在测试里复现（要求 `started=true` 且 `view=null`，而一旦收到过 state，
`view` 就不会再变回 null），所以 `ui-smoke` 里直接构造一个 `OnlineGame` 对象渲染 `RoomPage`。

### 邀请链接

`?room=ABCD`。用 query 参数而不是路径，因为这是静态站点：路径要配 history fallback，
而 `?room=` 在任何静态托管上都能直接打开。

- 房间页有「复制邀请链接」
- **记住过昵称的人**点链接，连上后直接进房（邀请的意图很明确）
- **第一次来的人**只把房间号填好，光标停在昵称框 —— 强行用「玩家」这个名字入座，
  以后在座位表里谁都认不出谁
- 参数读一次就从地址栏抹掉（`history.replaceState`），否则点「返回大厅」后刷新
  又会被自动拉回同一个房间，看起来像退不出去

### 协议

```
客户端 → 服务端   lobby
                 create { name, room?, isPublic?, password? }
                 join   { room, name, password? }
                 resume { room, token }
                 spectate { room, password? }          // 观战：不占座位
                 start  { playerCount, bots }
                 command { cmd }
                 takeback
                 rematch { ready? }                    // 再来一局：准备 / 取消准备
                 swapSeats { a, b }                    // 交换两个座位号
                 bots      { count }                   // 下一局的机器人数量（房主）
                 leave                                 // 主动离开（和掉线必须区分，见下）
                 ping
服务端 → 客户端   lobby  { rooms[] }               // 含 spectators 人数、hasPassword（不含密码）
                 joined { playerId, token, seat, room, host, resumed, spectator?, spectatorDelayRounds? }
                 room   { room, seats[], started, hostId, isPublic, spectators?, ready?, gameOver?, closed? }
                        // 每个座位：{ playerId, gamePlayerId, name, seat, connected, isBot, autopilot, left?, ready }
                        // connected=false 只是「连不上」；left=true 是「主动走了，不会回来」。
                        // 两个都下发，界面才能分开说「掉线」和「已离开」
                 state  { state, deadlineAt, autopilot }   // state 已按你的视角裁剪
```

时间参数都能用环境变量覆盖（测试里调小）：`ABS_TURN_TIMEOUT_MS` / `ABS_SEAT_GRACE_MS` / `ABS_BOT_STEP_MS` / `ABS_SPECTATOR_DELAY_ROUNDS` / `ABS_CLEANUP_MS`。
容量、防护、快照相关的环境变量见下面三节。

### 单端口：前端和 WebSocket 同一个服务

服务端不是「只跑 WebSocket」，它同时托管 `dist/`：

| 路径 | 行为 |
|---|---|
| `/`、任意无扩展名的路径 | 返回 `index.html`（`Cache-Control: no-cache`） |
| `/assets/index-XXXX.js` | 带内容哈希的产物，`max-age=31536000, immutable` |
| `/assets/不存在的.js` | 404（**不会**回落成 HTML —— 否则浏览器会把一段 HTML 当脚本执行，报错完全对不上问题） |
| `/healthz` | `{ ok, uptimeSec }`，不遍历任何房间，给进程守护用 |
| `/stats` | 连接数 / 房间数 / 对局数 / 限流次数 / 内存 / 当前上限，以及泄漏诊断字段（见下） |

为什么必须同端口：客户端生产环境连的是 `location.host`（`useOnlineGame.ts` 里的 `resolveWsUrl`），
分端口就得跨域、就得让用户自己配代理。同端口之后 `npm run serve` 一条命令就能直接发给朋友。

路径穿越（`%2e%2e%2f`）、空字节、非 GET/HEAD 都在这一层挡掉；解析成绝对路径后还会再校验一次
「必须还在 dist 里」—— 只靠字符串匹配 `..` 在 Windows 上有太多变体（`..\\`、大小写、编码斜杠）。

### 上限与防护

| 项 | 默认 | 环境变量 |
|---|---|---|
| 房间总数 | 200 | `ABS_MAX_ROOMS` |
| 连接总数 | 500 | `ABS_MAX_CONNECTIONS` |
| 单房观战位 | 20 | `ABS_MAX_SPECTATORS` |
| 单连接消息速率 | 100 条/秒（突发 200） | `ABS_MSG_RATE` / `ABS_MSG_BURST` |
| 单条消息体积 | 64 KB | `ABS_MAX_PAYLOAD` |

- 超速的连接不会立刻被杀：第一次只回一句「操作太频繁了」，连续超 20 次才断开（1008）
- 超体积的消息由 ws 自己关（1009）
- 连接数超了在 upgrade 阶段直接回 503，连 WebSocket 都不建
- 15 秒一次 WS 层 ping/pong：拔网线、合盖休眠这类「TCP 还开着但对端已经没了」的连接会被清掉
  （客户端 5 秒一次的 app 层 ping 管不到这种情况）
- 每条消息的整个分发过程包了 try/catch，`ws.on('error')` 也有人接 ——
  一个乱发包的客户端不该能把整台服务打挂。这条是实测踩出来的：不接 `error`，
  ws 内部抛的 `RangeError: Max payload size exceeded` 会直接升级成 `uncaughtException`
- 进程级还有 `uncaughtException` / `unhandledRejection` 兜底，一分钟内炸 10 次才退出等重启
- 数值型环境变量写错不会静默生效：会打一行 `[配置] XXX=... 不是合法数字` 并退回默认值。
  这条是踩出来的 —— `Number('20_000')` 是 `NaN`（下划线是数字字面量语法，不是字符串语法），
  而 `setTimeout(fn, NaN)` 等价于 0 毫秒，于是 `ABS_TURN_TIMEOUT_MS=20_000`
  会让「思考时间」变成「立刻超时、AI 接管」，界面看起来像所有人都在被托管

### 长跑：泄漏诊断

服务端要连续跑几小时，最难受的一类问题是「跑了一下午才开始变慢」——
症状出现时已经离现场很远了。`/stats` 因此直接暴露三张内部表的大小：

| 字段 | 正常值 | 含义 |
|---|---|---|
| `sessions` | 等于当前连接数 | `session: Map<ws, 座位信息>`，断线不清就是内存泄漏 |
| `seatedSockets` | 等于「在房间里的玩家数」 | `sockets: Map<playerId, ws>`，被 `leave` / 断线顶号漏删会一直涨 |
| `spectatorSessions` | 等于观战人数 | `spectatorRooms: Map<ws, roomId>` |

空闲时（没人在线、没有房间）这三个都应该是 **0**。`npm run test:server` 的
`[16]` 就是钉这个的：5 个房间 × 2 个真人走一遍「建房 → 加入 → 离开 → 断开」，
最后断言房间数没有增长、三张表全部归零。

写这条用例时踩过一次：一开始量到 3 个残留连接，差点当成服务端泄漏 ——
实际是测试脚手架自己有几个早期用例的客户端没关（只在大厅、从没进过房间）。
现在 `connect()` 会把所有客户端登记起来，收尾统一断开。

### 快照与重启恢复

进程重启（发版、崩溃、机器重启）时房间不会消失：

- 房间结构 + 引擎状态每 2 秒（`ABS_PERSIST_MS`）落一次盘；写临时文件再 `rename`，不会留下半截 JSON
- 启动时读回快照，**所有座位一律标记为离线**，走正常的 5 分钟保座 + token 重连路径
  —— 没有「只在重启后才走」的分支，也就没有只在重启后才出现的 bug
- 进行中的对局恢复后立刻交给 AI 托管，人回来点「我回来了」就交还
- 快照带版本号和**卡池指纹**：改了牌表 / 角色表之后老快照自动作废，
  不会带着对不上的牌 id 启动（改一句描述文案则不会让存档失效）
- 超过 12 小时的快照直接丢弃；文件坏了也只是「当作没有」，不影响启动
- `SIGINT` / `SIGTERM` 会先通知所有连接「服务要重启」、强刷一次快照、再关端口
- 通知用的是 `restart` 类型，**不是 `error`**。客户端的 `error` 分支语义是
  「回座失败 → 清掉座位存档、回大厅」，用错类型等于每次发版把所有在线玩家踢回大厅
- 运维排水：配了 `ABS_ADMIN_TOKEN` 之后可以主动触发同一条路径（不配则接口不存在，404）

  ```bash
  ABS_ADMIN_TOKEN=xxx npm run serve
  curl -X POST -H "x-abs-token: xxx" http://localhost:8787/admin/shutdown
  ```

- 目录默认 `./.abs-data/rooms.json`；`ABS_DATA_DIR=off` 可关闭（测试用）

`npm run test:prod` 会真的起子进程验证这一段：建房开局 → 杀进程 → 再起一个 → 凭 token 回原座，
并核对对局人数和轮次都没丢；还会验优雅排水（`/admin/shutdown` → 收到 `restart` → 进程正常退出 → 快照已强刷）。

这个测试曾经**偶发 4 条一起红**（「落盘内容里有进行中的对局」「恢复后能拿到对局状态」
「人数没丢」「进度没丢」），看起来像持久化回归，其实是等待条件写错了：

- 它等的是「文件里出现 `"RSTR"`」，然后立刻杀进程；
- 但房间是**开局前**就建好的，磁盘上第一份含 `RSTR` 的快照完全可能是「还没开局」那一版；
- 读到那一版就 break → 杀进程 → 留下的快照里没有对局 → 后面三条跟着一起红。

用探针实测过：开局前后每 10ms 采样一次 `rooms.json`，77 次采样里有 **20 次**
是「有房间但还没开局」（约 26% 的窗口），所以大约每四轮就会红一次。
现在等的是断言本身（`"RSTR"` **且** `"started":true`），连跑三轮 62/62。
教训和别处一样：**等待条件必须是断言本身，不能是替身**。

`npm run check:restart` 则是浏览器侧的那一半：**优雅排水**和**进程被强杀**各来一轮，
每轮都断言遮罩出现又消失、房间号不变、日志条数不减、恢复后还能出牌。

## 八、前端动效

方案是**纯 CSS + Web Animations API，零依赖**（包体仍 ~86KB gzip）。

| 效果 | 触发方式 | 实现 |
|---|---|---|
| 卡牌飞行 | `view.flow` 的 `(source → current)` 变化 | 克隆节点 + WAAPI 三段关键帧（中途上抛，走弧线） |
| 情报落位 | 某玩家情报列表多了一张 | `chipPop` 弹入 + 玩家卡 `landFlash` 高亮 |
| 回合横幅 | `view.round` 变大 | 绝对定位浮层，1.7 秒后自动消失 |
| 当前行动者 | `pending.player` 指向某人 | `actingGlow` 呼吸光晕 |
| 结算面板 | `winner` 出现 | 遮罩淡入 + 卡片弹入 + 获胜者逐个弹出 |
| 倒计时告急 | 剩余 ≤ 10 秒 | 变红 + 脉冲 |

**关键设计：所有动画由状态变化驱动，不由点击驱动。**
所以 AI 行动、热座切视角、联机对手操作，三种模式下看到的效果完全一致；
而且动画不会和 React 的渲染节奏打架 —— 飞行是「一次性、不参与状态」的视觉效果，
放进 React 每帧 `setState` 反而更容易出 bug。

飞行用的是克隆节点 + `element.animate()`，动画结束自删，组件卸载也不用善后。
不支持 WAAPI 的浏览器会直接跳过动画（代码里有 `try/catch` 兜底）。
另外全部动画都尊重系统「减少动态效果」设置（`prefers-reduced-motion`）。

## 九、下一步能接的东西

- 官方技能文本落地（纯数据替换，不动代码）
- 多进程 / 多实例：现在房间状态在单进程内存里，要横向扩容得先把 `rooms` 挪到 Redis
  之类的共享存储，并把「谁持有某个房间」做一次路由（现在只做了单机内的快照持久化）
- 账号体系：现在身份就是 localStorage 里的 `resumeToken`，换设备/清缓存就回不去了
- 回放：`GameState` 是纯数据 + 指令可重放，理论上存一串 `Command` 就能复盘整局

## 十、平衡现状（2026-10-27 实测）

`npm run balance` 300 局，5 人局，启发式 AI 对战：

| 阵营 | 胜率 |
|---|---|
| 红（潜伏） | 47.7% |
| 蓝（军情） | 42.0% |
| 特工 | 10.3% |

平均 4.8 轮结束，平均 190 次交互。座位胜场 36 / 59 / 67 / 77 / 61，无系统性先手优势
（纯随机策略对照：座位 26 / 29 / 31 / 34 / 30）。红蓝差 5.7% 在 300 局样本下约 1.4 个标准差，
不算显著偏置，但也没到「完全对称」，后续调数值时可以继续盯。

**两个已经踩过的坑，改卡池时别再踩：**

1. **卡池的颜色 × 功能分布必须均衡。**
   第一版卡池是「颜色、方式、功能各洗一次再按下标拼起来」生成的，结果【截获】11 张里 8 张是蓝色。
   【截获】是留在手里防守的牌，等于蓝方手里长期压着一堆蓝牌传不出去 —— 红方胜率直接被抬到 66%。
   现在 `gen-default-deck.ts` 改成按比例分配 + 全局修正的确定性算法，交叉分布偏差 ≤ 0.76 张。
   **改完配比一定要重跑 `npm run balance`**，数据层的偏置引擎查不出来。

2. **特工的胜利条件必须靠机制，不能靠调数字。**
   加机密任务之前，特工只能靠「收 6 张真情报」赢，实测胜率 1%；把 `agentWinIntelCount`
   从 6 调到 5 / 4 也只到 2.0% / 4.7% —— 因为红蓝双方都在主动避免把真情报给别人，数字改不动这件事。
   换成「完成机密任务即获胜」之后，特工胜率 1% → 12%，而且赢法变得多样（攒情报 / 保持干净 / 熬到有人出局 / 活到第 6 轮）。
   **这是这一版最有价值的一处改动：把一个死掉的阵营救回来了。**

   任务难度是调出来的：第一版 `surviveRounds 4` + `othersDead 2` 太便宜，特工胜率直接飙到 21%；
   收紧成 `surviveRounds 6` + `othersDead 3` 之后落到 12%。改任务数值后一定要重跑 `npm run balance`。

## 十一、已知取舍

- 服务端房间状态在内存里，靠**快照落盘 + 启动恢复**扛重启（最多丢 2 秒进度）。
  这不是数据库：快照是整份覆盖写的，只适合单机；多实例要换共享存储。
- 观战延迟是按回合的（落后 1 轮），不是按秒。一轮之内观众看到的画面是静止的，
  这是有意的 —— 换成秒数在慢局里太保守、快局里又不够。
- AI 只做启发式，不看对手手牌，也不会做复杂的功能牌连锁。它的定位是「规则正确、不犯蠢」。
- 动画只在 UI 层，`core/` 里没有任何动画概念。加新效果时也不要碰 `core/` ——
  引擎的输出是状态差，不是事件流，UI 自己从状态差里推断该放什么动画。
- 托管用的就是 AI 陪练那套启发式，所以「托管打得好不好」等于「AI 强不强」。
  现在它不犯蠢但也谈不上强，需要更强的话是 AI 层的事，和托管机制无关。
- **小窗口 / 手机上的对局页**：座位卡一多就把操作区推到折叠线以下，而「轮到你出牌，
  但按钮在屏幕外」是最容易被玩家骂的那类问题。做法是给操作区/手牌条开
  `position: sticky; bottom: 0` —— 内容装得下时它**等于没生效**，装不下才钉在底部，
  所以 1440×900 一点变化都没有，1280×720 和手机则不用再滚。
  窄屏额外三条：手牌改单排横向滚动（换行的话操作区高到把牌板盖死）、
  选角卡片改 2 列、座位卡锁 2 列（`auto-fill` 在 360 宽上会掉成单列，5 张卡纵向排开 706px）。
  矮屏（高度 < 700px）另外压状态条/目标条/牌面尺寸 —— 那里是**纵向预算**不够，跟宽度无关。
  **诚实的边界**：360×640 这种屏上，状态区 + 展开的操作区一共 380px，
  一张座位卡 154px 放不全 —— 那种尺寸只保证「能看清对面是谁（名字 + 角色）」，
  想看全情报格要往上滚。判据在 `check:viewports` 里按屏高分了两档，没有把标准偷偷降低。
  `npm run check:viewports` 在四个视口上各跑一遍并出图，
  断言里包括「吸底不能把牌板盖住」「角色名不竖排」「顶栏不折行」「日志不超过屏高 1/6」，
  以及手机上的**点击目标 ≥32×32**（44 是理想值，32 是底线；低于这个尺寸，
  触摸会因为「点在两个元素中间」而误触）。

  这项抓到的两个都在「看着像文字链接」的地方：顶栏 tab 只有 28px 高、
  结算页的「调整座位 / 人数」只有 16px 高（`padding: 0`）。
  修法不是把字放大，而是给按钮补 `padding` 再用负 `margin` 把多出来的高度吃掉 ——
  点击区变大、视觉位置和行高一点不变。

- **弃牌阶段是操作区最挤的状态**（手牌满 + 多选计数 + 确认按钮同时出现），
  360×640 实测操作区 210px、牌板只剩 117px。两个坑：
  1. `.actionbar-title` 是 flex 行，`<strong>` 默认 `flex-shrink: 1` ——
     后面的提示一长，**「弃牌阶段」被挤成「弃牌阶」/「段」两行**（和顶栏 tab 同类）。
     修法：`.actionbar-title strong { flex: none; white-space: nowrap }`，让路的是提示，不是标题。
  2. 「已选 X / N」原来塞在提示里，把提示顶成两行。挪到确认按钮旁边（`.sel-count`，
     选够了变金色）之后标题回到一行，操作区从 230px 降到 210px，
     而且这个数字是「按钮为什么点不动」的唯一解释，本来就该跟着手指走。
  3. 窄屏上 `.hand` 是 `overflow-x: auto`，而**按 CSS 规范这会把纵向也变成 auto** ——
     选中态的 `translateY(-4px)` 抬起的那几像素被容器上沿切掉：选中卡看着是「顶格」
     而不是「抬起」，而且那几像素连点都点不中（`elementFromPoint` 落到 `handzone`）。
     修法：给可点选的那条手牌行 `padding-top: 8px` 留出抬起空间
     （只读的手牌条没有选中态，不给）。
  判据在 `npm run check:discard`（本地热座 3 人局，两局都第一次就撞到弃牌，共 20 秒）。
  **要弃几张不是常数**：手牌 7 张时 `need=1`、8 张时 `need=2`。
  所以断言先读「已选 X / N」里的 N 再点够它 —— 写死「选一张按钮就该变可用」
  会在 `need=2` 的局里误红（实测遇到过一次，`已选 1 / 2`）。

- **响应窗口（截获 / 识破）是全游戏最挤的状态**：它要同时放阶段名、提示句、
  可选的牌、两个按钮，还要把牌板留在屏幕上。360×640 实测操作区 264px、
  **牌板只剩 3px**（等于看不见）。根因是同一句话被渲染了两遍：
  `redact.ts` 给的 `description` 是「有情报正在传递」，而 `engine.ts` 给的
  `pending.prompt` 是「有情报正在传递 —— 是否使用【截获】拿走它？」——
  后者以**严格前缀**的方式包含前者。修法不是删掉 `description`，
  而是判前缀：`descAdds = !prompt.includes(description)`，
  将来 prompt 不再包含它时这一行会自己回来。操作区 264 → **237px**，牌板可见 3 → 31px。

  这条状态还有两个专属判据，因为「牌板还剩多少」会随状态条折几行而变
  （实测 14px 和 31px 都出现过，直接卡阈值就是「十次红两次」）：
  1. **操作区高度预算**：≤ 屏高的 39%（640 上 = 250px）。237 过、264 红 ——
     这条才是真正挡住「再塞一行进去」的那道门。
  2. **牌板滚得出来**：把 `.board-wrap` 滚到视野顶部后，至少 1 张座位卡完整可见。
     注意不能「滚到底」—— 那时牌板已经被推出屏幕上方，量出来是 0/3。
  判据在 `npm run check:response`（本地热座 3 人局，两个视口都是第 1 局就撞到，共 20 秒）。

  另外 `.actionbar-title .hint` 加了 `text-wrap: balance`：360px 上那句提示折行时
  默认会留下「它?」两个字的孤儿行，均分之后变成「有情报正在传递 —— 是」/「否使用【截获】拿走它？」。
  `balance` 只改断点、不改行数，所以上面那条高度预算不受影响（实测仍是 237px）。

- **倒计时环两位变一位不会重排**（已证伪，留了断言防回归）。
  `CountdownRing` 的 `<b>` 从 30 数到 9 少一位，而它靠 `margin-left: auto`
  顶在状态条最右边 —— 理论上整条状态条会跟着重新折行、牌板下跳。
  实测 360×640 和 390×844 上环宽恒为 44 / 50px、`<b>` 恒 16px、状态条恒 33px，
  靠的是 `min-width: 16px` + `font-variant-numeric: tabular-nums`。
  断言不等到真倒数（等 21 秒既慢又会撞上服务端超时托管），而是在同一个同步
  `evaluate` 里把文本改成 30 / 9 再量回来 —— 同步执行，React 没机会插进来重渲染。


  老写法是 `ref={(el) => el && (el.scrollTop = el.scrollHeight)}` ——
  内联 ref 回调**每次渲染都会执行**，等于无条件滚到底。360×640 实测：
  往上翻到顶（`scrollTop 0`），对面一出牌就跳回 `199`（= 最底部），
  而那块只有 62px 高（不到 3 行），**历史根本读不了**。
  现在用一个 `stickRef` 记住「用户是不是贴着底」，只有贴底时才滚；
  用户翻回底部附近（24px 以内）自动恢复跟随。
  判据在 `check:viewports` 里成对出现：翻上去要停住、翻回底部要重新跟上 ——
  **只验前一半的话，一个「永远不滚」的实现也能过**，那比抢滚动更糟。

  **情报日志的「跟尾」也在这条自查里**：`LogPanel` 靠一个内联 ref 回调
  `el.scrollTop = el.scrollHeight` 让日志停在最新一条。很轻，也很容易被改坏
  （换成 `useEffect` 少写一个依赖、或者把 ref 删掉），而坏了的症状在窄屏上特别刺眼：
  360×640 的日志区只有 62px（不到 3 行），不跟尾时看到的是**最老的**几条，
  刚发生的事永远在下面看不见 —— 对观战者尤其致命，日志是他唯一的信息来源。

  这条断言只判用户可见的性质（最后一条是否落在日志区的可视范围内），
  但同时把「本次是否真的走到了滚动路径」打进一行 `·`：
  桌面和小笔记本的日志列很高，7 条也不溢出，那一行会写「未溢出（这条没走到滚动路径）」。
  **绿勾不代表滚动路径被测过** —— 与其让它在宽屏上假装通过，不如把这件事写在输出里。
  做过变异测试：删掉 ref 回调后 360 视口立刻红（`距底 170px`）。

  **但「不抢滚动」只解决了一半**：日志停住之后，新消息会静静堆在下面，
  而 360×640 的日志区只有 75px（两行多），用户没有任何线索知道「下面还有」。
  所以翻上去且有新消息时，右下角浮一颗 **「↓ N 条新消息」**（`.log-jump`）：
  `min-height: 32px` 保证点得准，点击回到底部并清零。未读数是
  「上次渲染的条数」和「这次」的差，只在 `stickRef` 为 false 时累加 ——
  贴底时永远不涨，翻回底部（24px 以内）自动清零。
  它**会盖住最下面约 1.4 行**：日志栏就 75px，32px 的点击高度省不掉，
  另一条路（给它预留空间）会永久少显示一行，更亏。判据在 `check:viewports`
  的 `logScrollRespect` 第三段：药丸出现 / 文案带数字 / 在日志区内 / ≥32px /
  点完距底 ≤2px / 点完消失。

  **这一段的四条是「必须全绿」而不是「没有就跳过」**：跑成了（翻上去了、
  也等到了新日志）却没出现药丸，四条一起判红。跳过会让「删掉药丸」这种回归
  安静地通过 —— 实测变异两次：
  ① 把渲染条件改成 `false &&` → 4 红（「药丸没有出现」）；
  ② 让点击只改 state、不真的滚到底 → 只红 1 条（`距底 200px`），
  说明这四条各测各的，不是一条断言的四个回音。

  **矮屏（高度 < 700px）的纵向预算**是另一条线：360×640 上「第一排座位卡的
  身份行必须露在吸底操作区上面」，而目标条的高度是**内容驱动**的 —— 抽到
  「存活到第 6 轮开始。」是 46px，抽到最长的那条机密任务（`core/tasks.ts` 的
  `noBlackWith`，再加上特工独有的「或集齐 N 张真情报」那行）是 97px，
  身份行正好被压在吸底操作区下面（实测余量 **−2px**）。

  所以这条断言不能靠随机抽到的任务去验，否则就是「五次红一次」的偶发失败：
  `check:viewports` 会把最长的那条文案**直接注入**再量（注入与测量在同一个
  `evaluate` 里，否则 React 会先重渲染覆盖掉），余量 ≥8px 才算过。

  吃掉高度的不是字号，是**换行结构**：`.goalbar` 原本是 `flex-wrap`，
  「军情局」这个标签是独立 flex 项，360 宽上它（55px）和正文（301px）挤不进
  一行，于是标签独占一行 —— 白占 22px，还让正文提前换行。矮屏上改成块级流 +
  标签 `inline-block`，标签并进正文首行：97px → **62px**，余量 −2 → **+34px**。
  字号一点没动（11.5px），文案一个字都没截 —— 任务是对局目标，看不全等于没法玩。
  另外几处省下来的空间来自行距（`row-gap` 8px 收到 2px）、内边距，以及手牌与
  操作区之间那个 12px 的纯装饰空隙（矮屏收到 6px）。

  ⚠ 改目标条样式要写进 `goal.css`，别写在 `styles.css`：三个 CSS 的引入顺序是
  `styles.css → online.css → goal.css`，同特异性的规则后到者赢，
  写在 `styles.css` 里的 `.goalbar` 规则会被 `goal.css` 静默覆盖
  （试过一次，规则完全没生效，还自以为改好了）。

  **手机横屏（844×390 一类）是另一套布局**。横屏的高度只有 338px（扣掉顶栏），
  竖排布局里「操作区 210px + 日志 62px」一叠，牌板一点都露不出来 ——
  实测操作区从 y=68 盖到 278，第一排座位卡的身份行被盖住 **188px**，
  横屏等于只能看见自己的手牌。而横屏的宽度是富裕的（844），所以横屏改成：
  操作区与日志移到**右侧固定栏**（320px，上面操作区、下面日志 120px），
  牌板独占左列整列高度。判据也跟着换 —— 横屏问的不是「身份行有没有被
  **下面的**操作区盖住」，而是「身份行在不在可视区里、**横向**有没有被右栏压住」。

  **横屏的右栏只有 218px 高（屏高 390 − 顶栏 52 − 日志 120），而操作区内容要 346px。**
  出牌阶段「标题 + 一行按钮」勉强放得下，情报阶段多一行「方式：密电 / 文本」、
  有时再加「接收者」和一句「这是你要收的红色情报」警告 —— 实测溢出 **129px**。
  栏本身是 `overflow-y: auto`，滚是能滚，但滚到中间时**一个按钮都看不见**：
  截图里右栏最后一行是「方式：密电 / 文本」，「传出这张情报」在栏外 129px。
  这就是「轮到我出牌，但按钮不在屏幕上」。

  修法：把最后一行操作按钮钉在栏底
  （`.battle-main > .actionbar > .action-row:last-child { position: sticky; bottom: 0 }`）。
  主按钮几乎总在最后一行 —— 出牌阶段的最后一行是【烧毁】/【试探】这类可选操作，
  主按钮「结束出牌」在它上面，钉住不会遮住它。

  ⚠ 这条**必须按最坏情况量**。只量「轮到我」那一帧是没用的：那一帧多半是出牌阶段，
  内容刚好装得下，把 `position: sticky` 改成 `static` 也照样绿（实测过）。
  所以断言会往最后一行之前**注入两行假的操作行**再量按钮位置，注入和测量在同一个
  `evaluate` 里做完（React 每秒重渲染一次，分两次调用注入的节点会被冲掉）。
  变异测试：改成 `static` 后立刻红（`按钮 321..354 / 栏 52..270`）。

  **日志栏的「标题 + 留白」在默认样式里吃掉将近一半**，小屏上最明显：
  `.log-head` 的 `padding: 12px 16px 8px` 固定占 40px，`.log-list` 自带
  `padding: 10px 16px 20px` 再吃掉 30px，`.log-item` 3px 上下内边距让节距变成 29px。
  而日志栏在小屏上只有：

  | 视口 | 日志栏高 | 标题占比 | 内容盒 | 能放几条 |
  |---|---|---|---|---|
  | 横屏 844×390 | 120px | 33% | 63px | 2 |
  | 竖屏 360×640 | 102px | **39%** | **32px** | **1** |
  | 竖屏 390×844 | 135px | 30% | 64px | 2 |

  **360×640 上只能看见 1 条日志** —— 玩家和观战者都一样，而观战者的唯一信息来源就是它。
  收三处留白（标题 `4px 12px` + 字号 11→10、列表 `2px 12px 4px`、条目 `2px 0`），
  **一个字都没删**，节距 29 → 27，结果：横屏 2 → **3 条**、360×640 1 → **2 条**、

  规则写在 `@media (max-width: 560px), (orientation: landscape) and (max-height: 520px)`
  里 —— 条件必须和「`.battle-side` 变矮」的那两个断点对齐；分成两份写，迟早只改一处。

  断言按「内容盒高度 ÷ 单条高度」算，不数「当前哪几条完整可见」——
  后者会被「刚好滚到某一条的一半」左右，换个条目长度结论就变。
  阈值分两档：横屏 ≥3 条、竖屏 ≥2 条（102px 的栏物理上放不下 3 条）。
  变异测试：**必须三处一起还原**才红 —— 只还原标题时 `内容 56 ÷ 27 = 2` 刚好卡在阈值上，
  断言仍是绿的，一度让我以为它空过。三处全还原后立刻红
  （`标题 40px + 列表 32px / 单条 29px ⇒ 1 条`）。
  做变异测试时，**改一半的「部分还原」可能恰好落在阈值边界上**，那不算证明。

  **观战者走的是另一条渲染路径**（`.spectator-panel`，没有操作区），横屏布局把它一起
  挪进右侧固定栏才完整 —— 不挪的话右栏空着 320px，而面板被挤到 y=666（屏高 390），
  得往下滚一大截才看得到「当时轮到谁 / 落后几轮」。竖屏里它仍在牌板下方，
  但「落后几轮」在顶部房间条里也有一份，所以不算信息丢失。
  这条由 `npm run shots:spectate` 顺带断言（面板在屏内 + 在右栏 + 牌板仍可读）。

  **进入观战不再弹「已进入观战」横幅**。房间条里常驻着一颗
  「观战中 · 只看公开信息 · 慢 N 轮」+「退出观战」，那句话是纯重复，
  却要多占 53px 高 + 22px 外边距，还要手动点「知道了」才收回去 ——
  而小屏正是最缺纵向空间的地方（360×640 的日志区只有 62px）。
  实测（360×640 观战首屏）：`.battle-main` 的 `scrollHeight` 669 → 594（少滚 75px），
  第 3 张座位卡从 386..540（正好贴着容器底边 540）上移到 311..465。

  ⚠ 量这笔账要看 **`scrollHeight`，不是 `clientHeight`**：`.battle-main` 是 `1fr`
  网格行里的滚动容器，高度由网格决定，删掉内容只会让 `scrollHeight` 变小，
  `clientHeight` 一动不动（488 → 488）。第一版注释按 `clientHeight` 写成了
  「488 → 553」，是错的 —— 探针一量就露馅。

  不改成「3 秒自动消失」：`notice` 是共用通道，里面混着「房间已关闭」这种**必须常驻**
  的提示，加定时器会误伤它们。对观众来说，页面直接切到对局界面 + 常驻 pill 已经是
  足够明确的反馈。`check:spectator` 每个视口断言一条「不弹这条横幅」。

  **结算浮层是「内容比屏幕高」的典型，单独有一条自查**（`npm run shots:result`）：
  它是打完一局才出现的，`check:viewports` 跑不到（每个视口都要真打完一局，太慢）。
  手机横屏带浏览器工具栏只有 330 高，而结算卡最坏情况（全员获胜 chip 两行 +
  「N 人掉线」提示行）有 328px。修前 `overflow: visible` + `align-items: center`，
  卡片**上下各裁一半**、而且滚不动 —— 标题和「再来一局」都够不着（实测 cardTop −11）。
  现在的写法是「浮层可滚 + 子项 `margin-block: auto`」：放得下时照旧居中，
  放不下时从顶部开始排、超出部分靠 `overflow-y: auto` 滚；
  短屏（`max-height: 520px`）再把卡片压一版（352 → 328），
  330 高上按钮直接可见，300 高这种极小横屏靠滚动兜底（脚本会真的滚到底再断言按钮够得着）。

  **「右栏空着」这件事被收成了一条不变量**（`scripts/lib/right-column.ts`）。
  横屏布局靠 `.battle-main { padding-right: 332px }` 把右边 320px 让出去，
  而「某个状态下那里没有组件」这个 bug 已经出现过三次：选角面板、观战面板、结算浮层。
  与其一个个想起来，不如让脚本自己去查：遍历 `.battle-main` 的直接子元素和 `.battle-side`，
  看有没有哪一块（≥200×80）真的盖住了最右侧那 320px。**判据不认类名**，
  以后再加面板（聊天、复盘、计时器）忘了挪进去，就会红。

  它现在覆盖三个状态，都在 `check:viewports` 的横屏视口里：
  `横屏等待别人时` / `横屏选角时` / `横屏轮到自己时`。
  观战那个状态不在 `check:viewports` 里（它要另一个浏览器上下文当观众），
  由 `shots:spectate` 调用同一个函数断言 —— 一份判据，两处使用。

  两个必须写死在这条不变量里的规则：
  - **横屏只能用视口尺寸判断**（`isSidewaysSize`）。用 `width > height` 会把
    小笔记本 1280×720 和桌面 1440×900 一起带进横屏分支，那里 `padding-right` 是 0。
  - **「没留右栏」不能算通过**。`rightColumnState` 把 `applicable` 单独返回：
    横屏却没留宽度是布局没生效，必须报失败；否则这条断言在别的视口上会靠
    `applicable=false` 悄悄变绿 —— 第一版就是这样，桌面和小笔记本各空过了 1 条，
    总数从 87 掉到 85 才是对的。

  这条断言做过**变异测试**：把 `padding-right` 临时改成 0，重构建后
  `ABS_VP=landscape` 立刻两条全红（`横屏没给右栏留宽度（padding-right=0px）`），
  还原后重新变绿。新写一条断言时，先想办法让它红一次，比看它绿可信。

  **另有一条断言被发现是数学恒真的**（第五次踩同一个坑）：
  原来横屏断言的是 `操作区高 + 日志高 <= 屏高`。但操作区是 `top:52 / bottom:120`
  固定定位 ⇒ 高度恒为 `屏高−172`；日志恒 120；两块相加 = `屏高−52`，
  **永远**小于屏高（实测 218+120=338 ≤ 390）。这条断言不可能失败。
  现在改成问几何相邻（`操作区底 <= 日志顶`，防止两块叠在一起），
  外加一条真正会坏的：「主按钮不用在栏里滚就看得见」（见上面横屏那一节）。

  `ABS_VP=360 npm run check:viewports` 只跑一个视口。五个视口一轮四分多钟，
  调一条窄屏断言时不该每次都等全量。

  **房间页会继承大厅的滚动位置**（三屏共用一个滚动容器，换屏时没人归零）。
  这一条是顺着「横屏房间页的『开始对局』在折叠线下面 155px」查出来的，
  但它比原来那个问题严重得多。

  结构上的原因：`BattlePage` 里只有一个
  `<div style={{ flex:1, minHeight:0, overflow:'auto' }}>`，
  大厅 / 房间 / 对局三屏都渲染在它里面。React 换屏时只换子节点、**不换容器**，
  于是滚动位置跟着容器一起留下来。

  滚动是「点击」自己带进来的，而且**发生在换屏之前**：为了够到大厅底部的
  「创建并进入」，浏览器先把这个容器 scroll-into-view。给容器挂 scroll 监听实测
  （844×390，点「创建并进入」）：

  | 时刻 | scrollTop / max | 当时是哪一屏 |
  | --- | --- | --- |
  | t=344ms | 232 / 1625 | 大厅 ← 点击前的 scroll-into-view |
  | t=363ms | 0 / 248 | 房间 ← 换屏同一帧归零（修复后的 trace） |

  房间页的 max 只有 248，232 连钳都不用钳，原样带进去 ——
  一打开就滚在下半截：「房间号」和「复制邀请链接」被顶到容器可视区上方
  （邀请按钮 top = 9，容器可视顶边 113）。

  360×640 上更彻底：大厅 max 5810，点击时直接滚到底（top 5810），
  换屏后被钳到房间页的 max 286 —— **房间页一打开就是最底下**。
  房间号、邀请链接全在屏外，而这正是玩家最需要念给朋友的那两样，
  而且屏幕上没有任何线索提示「上面还有东西」。

  **修法**：`useLayoutEffect` 里比较容器的 `firstElementChild`，变了就
  `scrollTop = 0`。不用「当前是第几屏」的字符串 —— 那等于把 `OnlineFlow` 里的
  `inGame` / `inRoom` / 观战过渡态再抄一遍，抄漏一处就是下一个 bug；
  `.lobby` / `.room` / `.battle` / `.launch` 是四个不同组件的根节点，
  换屏时 React 必然换掉这个元素，用它当身份不需要额外维护。
  用 `useLayoutEffect` 而不是 `useEffect`：后者在绘制之后才跑，会先闪一帧错误位置。

  **为什么以前的断言看不见这件事**：房间页原来只查了
  「没有横向溢出」和「房间号够得着」，而 `reachable()` 的第一步就是
  `scrollIntoViewIfNeeded()` —— 它自己把页面滚回去了，量的是
  「滚一下够不够得着」，玩家抱怨的是「一打开就看不见」。
  变异测试时这一点被直接证实：把归零改回空操作后，新加的两条全红，
  而 `房间号够得着（朋友要念的就是它）` **依然是绿的**。

  新加的两条（`check:viewports` 的房间页段，必须排在 `reachable` **之前**量）：
  - `进房间页时滚动位置归零（不继承大厅滚到哪儿）` —— 判 `scrollTop === 0`，
    详情里带 `scrollTop / max`；`max === 0` 的视口会额外注明「本来就装得下」，
    免得在桌面视口上假装通过。
  - `房间号 + 邀请入口不用滚就在屏内` —— 判 `.room-head` 整块落在
    最近那个**可滚动**祖先的可视区内（不是视口，也不是 `document.scrollingElement`）。

  变异测试实测（`el.scrollTop = 0` → `el.scrollTop = el.scrollTop`）：
  ```
  844×390   scrollTop 119/248 · 头部块 22..155 / 可视 113..390   ← 被裁 91px
  360×640   scrollTop 286/286 · 头部块 -145..41 / 可视 113..640  ← 整块在屏外
  ```
  注意横屏这里是 119 而不是上面 trace 里的 232：滚动多少取决于点击前
  **已经**滚到哪儿（`check:viewports` 在大厅里先 `reachable('.lobby-panel')` 滚过一次）。
  所以断言判的是 `=== 0`，而不是某个具体数字。

  360×640 的对照图（同一路径、同一时刻，只有归零那行代码不同）：
  `shots/before-room-scroll-leak.png`（`scrollTop 286/286`，第一张座位卡被横切、
  房间号整块不见）→ `shots/after-room-scroll-fixed.png`（`scrollTop 0/286`）。

  **还没解决的**：修好之后房间页确实从顶部打开，但它在矮屏上**本来就装不下** ——
  844×390 要 525px 内容、容器只有 277px，「开始对局」在折叠线下方 155px；
  360×640 差 193px。房间页现在靠滚动兜底（滚得到，但没有提示）。
  下一轮查这个：横屏 844 宽完全可以排成 7 列一行（现在座位网格在 844 宽上仍是 5 列，
  第二行只有 2 个座位），光这一项就能省下约 90px。

  **房间页在矮屏上装不下，主操作必须吸底。** 修完上一节的滚动泄漏之后，
  房间页确实从顶部打开了，但「开始对局」仍然在折叠线下面。逐块量下来：

  | 视口 | 滚动容器 | 内容 | 超出 | 「开始对局」位置 |
  | --- | --- | --- | --- | --- |
  | 844×390 | 277px | 525px | 248px | 545..578（折叠线 390，差 155px） |
  | 360×640 | 527px | 813px | 286px | 833..866（差 193px） |

  844×390 的 525px 拆开是：`padding 28 + room-head 133 + 间距 24 + 座位标题 27
  + 座位网格 177（2 行）+ 间距 24 + 操作条 52 + padding 60`。
  座位网格在 844 宽上只有 **5 列**（`minmax(128px, 1fr)` 的 auto-fill 算出来 5.9），
  7 个座位排成 5+2 两行 = 177px；排成 7 列能省 93px。

  但**光靠省是不够的**：28+133+27+84+52 已经是 324px，还没算间距。
  这一页在 390 高的横屏上就是放不下，再怎么收留白也得滚。
  所以这轮只做一件正确的事：**让主操作永远在屏幕上**——
  `.room-actions` 加 `position: sticky; bottom: 0`，和横屏对局页的
  `.action-row:last-child` 同一招。另外把 `.room` 的 `padding-bottom`
  在 `max-height: 700px` 下从 60px 收到 12px（那 60px 是纯留白，占溢出的 1/4，
  而且留 60px 的话滚到最底时吸底条会往上跳一下）。

  **不套媒体查询**：页面装得下时 `position: sticky` 是空操作（元素本来就在
  可视区里），只有真溢出才生效。这样不用猜「矮屏」的阈值，也不会在
  390×844 这种「只差 33px」的尺寸上漏掉。
  实测三档：844×390 按钮 `357..390`（可视底 390，钉住）、
  360×640 `607..640`（可视底 640）、1280×720 `452..485`（原本就够，没被挪动）。

  顺手删掉了一条**会骗人的设计**：吸底条原来加了
  `box-shadow: 0 -8px 10px -8px`（提示「下面还有内容」）。但页面装得下时
  sticky 不生效，那道阴影就变成一条凭空出现的灰带 —— 1280×720 截图里
  分隔线上方明显多了一道。分隔改由 `border-top` 承担，阴影不要了。

  断言只有一条，判「主按钮不用滚就整块落在滚动容器可视区内」：
  `房间页的主按钮不用滚就在屏内（矮屏吸底）`。
  变异测试（`position: sticky` → `static`）：
  ```
  844×390   按钮 545..578 / 可视 113..390 / 溢出 200px   ← 折叠线下方 155px
  360×640   按钮 833..866 / 可视 113..640 / 溢出 238px   ← 下方 193px
  1280×720  绿（本来就装得下）
  ```
  ⚠ 宽屏上这条**是空过的**。`check()` 只在失败时打印 detail，所以第一版把
  「本视口装得下，测不到吸底」写进 detail 等于没写 —— 绿的时候根本看不见。
  现在改成单独一行 `· 房间页本视口装得下（溢出 0px），这条测不到吸底`，
  和小笔记本/桌面各出现一次。

  **还没解决的**：这一页在 390 高的横屏上仍然要滚 200px 才看得到座位表
  （吸底条占掉 52px，剩下的 225px 刚够 room-head）。真要一屏放下得在横屏

  比这轮风险大，先记着。另外「准备下一局」那一态的操作条在 360 宽上

  都是这个形状：给桌面设计的视觉手段，在窄屏上被折行拆散）。

  左边必须在**同一行上**有兄弟顶着（`o.right <= k.left` 且纵向区间有重叠）。

  这一轮的发现方式很直接：`check:viewports` 的流程是「大厅 → 房间 → 对局」，
  全是联机；顶栏右边那颗「数据配置」在每个尺寸上都点得到，却一次都没被点过。

  实测 360×640（`.config` 内容宽 312px）：

  ```
  「传递方式」竖成 4 行（列宽 36px）
  「效果文本」竖成 4 行
  `id` 列只剩一个字符
  tab 栏 4 个 tab 各竖成 3 行（「身份与规则」= 身/份/与/规/则）
  ```

  这和 `角色名不竖排（一行放得下）` 是**同一个坏法**，只是没人查这一页。

  两处原因不同，所以两处修法也不同：

  1. **表格**：列宽本来是 `th style={{ width }}` 声明好的（卡牌表 42+90+130+
     80+90+110+50 = 592），但 `table.grid { width: 100% }` 让它在 312px 的容器里
     被强行压缩。修法：每张表一个**放得下所有声明列宽**的 `min-width`
     （写在 JSX 里，五张表分别是 720 / 910 / 520 / 480 / 520），外面套一层
     `.grid-scroll`，只让**表格自己**横向滚。
     不把 `.config` 变成横向滚动容器 —— 那样标题、工具栏、tab 会跟着一起滑走，
     手指刚点的按钮会从指头下面跑掉。

  2. **tab 栏**：`display: flex` 的子项默认 `flex-shrink: 1`，会**缩到
     min-content 就停**，不会均分剩余空间。所以 4 个 tab 缩成 70/63/66/62
     （每个 3 行），而右边还空着 45px。修法：`flex: 0 0 auto; white-space: nowrap`
     + 窄屏把内边距从 14 收到 8（4 个 tab 合计 345 → 297，312 放得下）。
     `overflow-x: auto` 留着兜更窄的屏，但 360 上四颗都在一行里。

  **代价必须写清楚**：横向滚动容器**必然**杀死内部的 `position: sticky`。
  1280×720 把 `.config` 滚 300px 实测：

  ```
  外层 overflow-x: auto   → 表头 top 43（跟着滚走）
  外层 overflow: visible  → 表头 top 72（= 容器顶 52 + padding 20，吸住）
  ```

  所以只在**真的放不下**的宽度上开滚动：最宽的角色表声明列宽合计 910，
  加 `.config` 左右各 24 的 padding = 958 ⇒ `@media (max-width: 960px)`。
  960 以上一律不滚，桌面保住吸头；960 以下让表格横向滚，吸头按设计放弃
  （自检里那一条只在 `vp.width > 960` 时断言，窄屏会打一行
  `· 窄屏让表格横向滚，吸头按设计放弃`）。

  新增四条断言（`check:viewports` 的第 0 段，放在联机流程**之前** ——
  对局中切到数据配置会把联机 hook 卸载掉，那是另一件事）：
  - `本地启动页没有横向溢出`（单机玩家打开应用看到的第一屏，同样零覆盖）
  - `数据配置没有横向溢出（横向滚动只发生在表格里）`
  - `数据配置的表头不竖排（中文最多 2 行）`
  - `数据配置的 tab 栏不竖排（每个 tab 一行）`
  - `宽屏上表格吸头还在（滚 300px 后停在容器顶边）`

  行数算法有个坑：`th` 是 `padding: 8px 10px` + `border-bottom: 1.5px`，
  直接 `高度 / 行高` 会把「一行」算成两行（36 / 19.55 ≈ 1.84），必须先减内边距。
  另外同一行里的 `th` 高度都一样（行高由最高的那格决定），所以「最坏的那一格」
  要按**文字最长**挑 —— 否则报出来的是只有 1 个字的「#」。

  1. `.room-row` 是 `display: flex`，**没有 `flex-wrap`** —— 房间号 + 两个按钮

  2. `.room-meta` 是 `flex: 1`，也就是 `flex-basis: 0`。折行判定比的是
     **假想主轴尺寸 = flex-basis**，basis 为 0 就永远「装得下」，所以
     **光加 `flex-wrap: wrap` 也不会折**。再叠上 `min-width: 0`（允许压到 0），
     中文就一字一行地竖排下去了。
